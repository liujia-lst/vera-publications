Maintenance options

The first phase is a standalone GitHub Pages publication list, organized by topic. Kanda should be able to add a paper, change its details and add a topic without editing HTML. The editing tool has not yet been selected.

Suggested direction: use Google Sheets if the team can maintain a shared Google account/workspace and publish the bibliography data. If that is inconvenient, start with the browser form and GitHub upload supplied with this draft. Consider a CMS when a full team website needs a shared editorial workflow.

1. Google Sheets

Use two tabs: Publications and Topics. The first holds title, authors, year, venue, paper URL, remarks and topics. The second holds the available category names. Keep record IDs in a protected column so existing rows can be updated reliably.

Topic dropdowns can use a range from the Topics tab. Google Sheets supports multiple selections in chip-format dropdowns on desktop; its documentation notes that this is not supported on mobile. New topics then need only a new row in the topic list, with no website code change. Google Sheets dropdown documentation.

Publish only the bibliography tabs as CSV. A build job should read and validate the exports before publishing a new static snapshot. Visitors then read the saved website rather than relying on Google Sheets for each page view. If an import fails, keep the previous successful deployment. This is the proposed implementation, not a built-in Sheets-to-GitHub feature.

Google documents that published content can update automatically, may take a few minutes, and can be restricted by work or school account policies. The team must confirm that public publication data may be exposed through this route. Do not put internal comments or unpublished information in the published tabs. Google publishing documentation.

Prepared in this delivery: CSV exports of the 258 records and ten proposed categories, a validated CSV importer and a Google Sheets download adapter. Still needed after selection: create the shared sheet, configure its dropdowns and permissions, supply its two CSV URLs and choose the update trigger. No live sheet or scheduled sync has been created.

2. Decap CMS

Configure a publication form containing the required fields and a separate Topics collection. A relation field can let Kanda select existing topics; a topic form can add a new category. Content is stored in the repository, so GitHub retains its history.

The standard GitHub backend requires editors to have push access. Its login flow also needs an authentication service or proxy; it does not work simply by placing an administrator page on GitHub Pages. This additional service needs an owner after the current developers leave. Decap GitHub backend; authentication and backend configuration.

Status: researched as an alternative; not installed or connected. Its account, authentication and hosting arrangement should be agreed before implementation. This makes more sense if the future team website also needs editable people, project and news pages.

3. Browser form and GitHub upload

The supplied editor implements the basic workflow now. Kanda can select a paper, update its fields, select multiple topics, add a topic and save a draft. She then downloads one complete catalog.json file and replaces the repository's copy through GitHub's upload interface.

The form does not ask for a GitHub token and cannot publish directly. Drafts remain in the browser; the downloaded file is the handoff to GitHub. Repository write access is required for the upload. An invalid catalogue fails validation before a new deployment.

This is suitable for occasional updates by one main maintainer. For concurrent editors, the shared sheet or CMS has a clearer workflow. Start each editing session from the current repository file; a whole-file upload from an old browser draft could undo a newer change.

Status: editor, data export, validation and GitHub Pages workflow are implemented. Data and build checks have passed. Browser interaction and the live GitHub deployment still require verification. GitHub Pages workflow documentation.

Decisions to make with the team

  • Choose one primary editing method and the account or team organization that will own it.
  • Have Kanda try adding one paper and one category before choosing the permanent workflow.
  • Compare the proposed category assignments with the missing tagged HTML attachment. The forwarded email contains examples, not the complete tagged list.
  • Confirm how the lab wants to handle source entries without a paper link and its 2027 section. The draft preserves all 258 source entries.
